# Rubric: is this a good first issue?

## Checks

Measure ages against the bundle's capture date in eval mode and today's date in live mode. Use only bundle evidence in eval mode. In live mode, apply the scope's house rules when interpreting claim evidence. A label or star count alone never establishes a pass.

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Open and writable | Issue state and archived flag in the bundle's Issue and Repo facts; live issue header and repository metadata. | The issue is open and the repository is not archived. | required |
| Human maintenance | Repo facts: last 5 default-branch commits with authors, maintainer first-response sample, and issue comment dates/author_association. Live: those same surfaces in references/evidence-guide.md; inspect the author of a bot-merged contribution. | At least one of: a human-authored default-branch change within 90 days (including a bot merge of human work); at least one owner/member/collaborator first response within 30 days of an issue opening in the supplied or latest 5-issue sample; or an owner/member/collaborator comment in this thread within 90 days. Automated updates alone do not count. | required |
| Recent use signal | Repo facts: latest release date and last push to any branch. Live: Releases and repository push metadata, as mapped in references/evidence-guide.md. | At least one release within 365 days or one push within 180 days. No release is needed if the push threshold passes. Stars alone do not count. | required |
| Bounded contribution | Issue body, full available comment thread, creation date, and closed-unmerged attempt history; live issue and Development sidebar plus thread references. | There is one identifiable contribution outcome and zero explicit blockers: an umbrella/tracking issue intended to split into independent contributions; an unresolved product/design debate blocking the requested behavior; or a maintainer explicitly requiring a core parser/compiler or architectural redesign. Do not infer these blockers from file count, a checklist, optional suggestions, or multiple diagnosed causes of the same bug. A docs page with supporting page updates is one outcome; a maintainer-diagnosed bug need not prescribe one implementation algorithm. Reject pure usage/support questions or a wish with no defined behavior. Also reject an issue older than 730 days with at least 2 abandoned implementation attempts. A short body, missing repro, or absent good-first-issue label does not by itself fail this check. | required |
| Available work | Repo facts: assignees and linked PR states; issue comments for claims, assignments, withdrawals and PR references. Live: Assignees, Development, full thread and status of referenced PRs; thread evidence overrides an empty sidebar. | Zero current assignees, zero open implementation PRs, and zero unwithdrawn claims with activity in the last 90 days. An old maintainer endorsement does not renew that clock: without a current assignment, open PR, or claim progress within 90 days, the old claim is stale. A closed-unmerged attempt is not an active claim. A referenced implementation PR without evidence of closure is unresolved claim evidence, not proof of availability. In live mode, ignore other students' claim signals as scope.md requires; do not treat a shared classroom issue as unavailable for that reason. | required |
| AI-assisted workflow allowed | Repo facts: contribution policy. Live: root or .github/ CONTRIBUTING.md, linked contributor docs, AI_POLICY.md / AI_USAGE_POLICY.md, AGENTS.md and contribution templates. | No outright ban on AI-assisted contributions. Disclosure, personal understanding, testing or human-review requirements pass as conditions to follow. A ban only on fully AI-generated work passes if assistive use is explicitly allowed. No AI policy passes after the policy locations have been checked; an inaccessible policy is unclear, not silence. | required |
| Verification anchor | Issue body and comments: input/output examples, reproduction steps, acceptance criteria or named test targets. Live: the same issue/thread sources. | At least one concrete input/output example, executable reproduction, acceptance criterion, or named regression-test target is present. | preferred |

## Verdict rule

Accept if and only if every required check is `pass`. A required `fail` or `unclear` rejects the issue. Use `unclear` when necessary evidence is genuinely missing after checking the named sources, not as a substitute for looking. Preferred checks never change the verdict; report their grades and use passes to rank accepted candidates together with the live scope's fit profile. No personal language preference or good-first-issue label can override a required result.
