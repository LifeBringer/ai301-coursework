# Procedure: how this tool grades a PR package

## Read order

1. Decide the mode. A bundle file with `## Repo facts`, `## Issue`, `## Thread highlights`, `## Plan context` and `## Candidate PR` is eval mode: the bundle is the only evidence, and `scope.md` and `voice-guide.md` are not read. An issue URL plus the student's `plan.md`, branch, `pr_draft.md` and `test_evidence.md` is live mode.
2. Live mode only: read `scope.md` before anything else. If its `Repo:` line still holds a bracketed placeholder, stop and tell the student to fill the `Repo:` line in `scope.md` with their section's Path Review repo; do not grade. If the issue URL is not in the scoped repo, refuse to grade. Note the house rules it lists.
3. Read `rubric.md` and write down the check names in table order (Plan fidelity, Decisive test evidence, Repo checks reported, Reviewable diff, Template and policy asks, Calibrated claims), which are required, and the verdict rule. Then read `references/evidence-guide.md`, the map for where each check's evidence lives.
4. Read the package in this order, the whole package before grading anything, and keep notes:
   1. Repo facts (live: `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md`, and the house rules from `scope.md`). Copy every template section, checklist item, required artifact, named check and AI-policy sentence exactly.
   2. Issue and thread (live: `gh issue view <number> -R <owner/repo> --json author,body,comments --jq '.author.login, .body, (.comments[] | {author: .author.login, role: .authorAssociation, body})'`, which prints each commenter's role). Note the reported failure. For each comment by an owner, member, collaborator or maintainer, note anything it asks of the PR; comments by others are context only.
   3. Plan context (live: `plan.md`, including `## Deviations`). Write the plan ledger: (a) every change the plan commits to, with its file or location; (b) everything the plan scopes out; (c) every test-plan item, marked `reproduced failure` when it re-runs something the repro evidence showed failing (each failure mode, input or failing test) or `other` (a control, a regression or edge case, a check of new behavior the plan adds), with its expected fixed result; (d) every check or suite command the plan names; (e) every deviation note.
   4. Diff and commits (live: `git diff main...HEAD` and `git log --oneline main..HEAD` in the working copy; only committed changes count).
   5. Test evidence (live: `test_evidence.md` and any output pasted in the description).
   6. Title and description last (live: `pr_draft.md`, first line the title, the rest the description).

   The plan comes before the diff because it is the yardstick: the diff is measured against what was promised, not the other way round. The description comes last on purpose, because it is a set of claims to check against the diff and the evidence; read first, a confident description sets what the diff "means".

## Evidence gathering

1. Gather each family from the locations the evidence guide names. In eval mode quote bundle lines and never fetch or read anything else. In live mode use only read-only commands (`git diff`, `git log`, `git status`, `gh issue view`, the GitHub API) and file reads; never edit, stage, commit, push, post, install, or run the student's code or tests.
2. Diff against plan (Plan fidelity, Reviewable diff): go through the diff hunk by hunk. For each hunk record the file, what it changes in one line, and one tag: `planned` (matches a plan-ledger change, including an import, helper or signature change that only serves it), `test`, `docs` (docs, changelog or a generated or lock file the change needs), `deviation` (matches a deviation note that says what and why), `scoped-out` (something the plan ledger excludes), `unplanned` (a behavior change the plan never names), or `debris` (debug output, temporary logging, commented-out code, dead code, formatting or whitespace churn, drive-by rename or refactor, an unrelated file, a draft or personal file). Then list every plan-ledger change with no hunk, and whether the PR states its absence.
3. Description against diff (Plan fidelity): list each claim the description makes about the change (fidelity statements such as "exactly as planned" or "no other changes", each bullet in a changes list, "adds a test", files or behaviors named). Tag each `matches`, `contradicted` (quote the hunk) or `unverifiable`.
4. Evidence against test plan (Decisive test evidence): for each `reproduced failure` item from the plan ledger, find its run in the evidence. Record the command or test name, the observed after-output, the before-result (from the evidence or the plan's repro), and whether it went through the path that failed or only a control. Record `not shown` for a reproduced failure with no run, and whether the PR explains its absence. For each `other` item, record only whether it is named with a stated outcome; it needs no pasted output.
5. Named checks against outcomes (Repo checks reported): for each command or suite the template, contribution guide or plan says to run, record its outcome, shown (pass line, count, exit status, pasted output) or stated in a sentence that names the check, or `not reported`, or the stated reason it was not run or failed. A checklist attestation that is not a command ("code formatted", "text internationalised") is recorded in step 6, not here.
6. Asks against the PR (Template and policy asks): for each template section, checklist item and required artifact from step 4.1 of Read order, record where the PR meets it (description section, prose sentence, or diff file) or `missing`. Quote the AI-policy ask and the PR sentence that meets it, or record its absence. For each maintainer ask from step 4.2, quote where the PR follows or answers it, or record that it does not.
7. Claims against evidence (Calibrated claims): record the title, and each certainty, coverage or impact statement in the description next to the evidence that does or does not back it.
8. Record evidence once and reuse it. If a source is genuinely missing from every location the guide names, record `absent` with the locations read.

## Check execution

1. Grade the checks in rubric table order. Plan fidelity comes first because the hunk tags from gathering step 2 also feed Reviewable diff, and the plan ledger it settles is what Decisive test evidence is measured against.
2. For each check, apply only that row's pass condition to the evidence recorded for it, and grade it `pass`, `fail` or `unclear`, with one line naming the fact or quote that decided it.
3. Map the tags directly: any `scoped-out` or `unplanned` hunk, any undisclosed missing plan change, or any `contradicted` description claim fails Plan fidelity. Any `debris` hunk fails Reviewable diff; an `unplanned` hunk that touches code the fix does not need also fails Reviewable diff. Any reproduced failure `not shown` without an explanation, or shown only through a control, fails Decisive test evidence; an `other` item reported in prose does not. Any named check `not reported` fails Repo checks reported. Any ask recorded `missing` fails Template and policy asks.
4. When the PR leaves out something the pass condition requires it to show or say, grade `fail`. Use `unclear` only when the package lacks a source the check needs and the PR author could not have supplied it, for example a bundle with no plan context.
5. Grade each check on its own evidence. A failure in one check never lowers another check's grade, and a strong check never rescues a weak one. A finding that legitimately meets two pass conditions (an unrelated hunk under a description that says "no other changes") fails both.
6. Grade substance, not presentation. Length, headings, polish and confident tone are not evidence; an honest, plainly stated shortfall is not a failure by itself.
7. Re-read the package only for a check whose evidence was not recorded during gathering. When the evidence supports both a pass and a fail reading, decide by the literal pass condition and mention the tension in the summary.

## Verdict assembly

1. Take the five required grades: Plan fidelity, Decisive test evidence, Repo checks reported, Reviewable diff, Template and policy asks.
2. If all five are `pass`, the verdict is `accept`. If any is `fail` or `unclear`, the verdict is `reject`. There is no other verdict.
3. Calibrated claims is preferred: include its grade and evidence, but never let it change the verdict.
4. Write a short summary with one line per check. For a reject, name the first failing or unclear required check in table order as the deciding check and quote its deciding evidence; list any other failing checks after it. For an accept, name the check that came closest to failing and why it still passed.
5. Live mode only: compare the title and description in `pr_draft.md` with each rule in `voice-guide.md` and quote any rule they break next to the breaking sentence. Voice findings never change the verdict. Also report any uncommitted change that looks like part of the fix, and any step of this procedure that did not fit the package, rather than improvising around it.
6. End with the fenced JSON block from `SKILL.md`: the item (bundle id, or the issue or PR URL in live mode), all six checks in table order using the rubric's check names, and the verdict. Nothing follows the JSON block.
