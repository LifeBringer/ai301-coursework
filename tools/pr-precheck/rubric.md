# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Plan fidelity | Every hunk of the diff, read against the plan's scope, named files, approach steps and out-of-scope list, plus any deviation note in the plan or the PR description; then the description's claims about what the PR does, read against the same diff (Plan fidelity in the evidence guide). | Every behavior change in the diff is one the plan commits to, or a test, doc or changelog entry for it, or is covered by a deviation note that says what changed and why the fix needed it. Nothing the plan explicitly scoped out appears (no new option, flag, setting, API, rename or rewrite the plan excluded or never named). Every change the plan commits to is in the diff, or its absence is stated in the PR or a deviation note. Every claim the description makes about the diff ("implements the plan exactly", "no other changes", "adds a test", a list of changes) is true of the diff. A smaller or different change passes when the PR states the difference and why; an undisclosed one fails. | required |
| Decisive test evidence | The test evidence and anything the description pastes, read against the plan's test plan and the reproduction evidence it re-runs (Test evidence). | For every reproduced failure the plan's test plan says to re-run (each failure mode, input or failing test the repro evidence showed failing), the evidence shows the run on the changed code (a command or test name with its observed after-output), and that output is the plan's expected fixed result or visibly differs from the reproduced before-result. The run must go through the path that failed: a control, a different input, or an unchanged path that never broke does not stand in for it. A reproduced failure that was not re-run passes only if the PR says so and why. Other test-plan items (controls, regression or edge cases, checks of new behavior the plan adds, suite runs) need only be named with a stated outcome; they do not need pasted output. Prose such as "tested locally", "works now" or "tests pass" in place of the reproduced failure's re-run does not count. | required |
| Repo checks reported | The commands or suites the repo's PR template or contribution guide says to run, and any suite or check command the plan's test plan names, read against the outcomes shown in the test evidence or description (Test evidence). | Each such check is named with its outcome, either shown (a pass line, a count, an exit status, pasted output) or stated in a sentence that names the check ("`go test ./...` passes", "cargo test passes (614 tests)", "fmt and clippy clean"), or the PR says it was not run or failed and why. A check that does not apply (for example a suite with no tests) passes when its actual outcome is reported as is. Template checklist attestations that are not a command to run ("code formatted", "text internationalised", "docs updated") are graded under Template and policy asks, not here. If neither the repo nor the plan names any check to run, this check passes. An unnamed "tests pass", or a ticked box with no outcome behind it, does not count. | required |
| Reviewable diff | The unified diff hunk by hunk and the commit list, read against the plan's files and approach (Diff quality). | Every hunk is part of the fix, its tests, its docs or changelog, or a generated or lock file the change needs. No debug output or temporary logging, commented-out code, dead or unreachable code, unrelated formatting or whitespace churn, drive-by refactors or renames, edits to files the fix does not need, or stray personal or draft files (in live mode: plan.md, comment.md, pr_draft.md, test_evidence.md, notes, scratch scripts). An unrelated hunk fails this check even when the description admits it, because it still has to be reviewed with the fix; it belongs in its own PR. | required |
| Template and policy asks | The repo's stated PR-template sections and checklist, contribution-guide asks and AI-use policy (the repo-facts block; live: the PR template, docs/CONTRIBUTING.md and scope.md's house rules), read against the title, description, commits and diff; plus explicit maintainer asks about the PR in the thread (Standards and comms). | Each section or item the template or guide asks for is answered with real content, in its own section or in plain prose: not left blank, not placeholder text, not "N/A" without a reason when the item applies. Each required artifact the asks name (an issue link such as "Closes #N", a changelog or whatsnew entry, updated docs or generated files, tests) is in the PR, or the PR shows why it does not apply. Where the repo states an AI-use policy, the PR meets it in the stated form; treat every package as AI-assisted work, so silence does not meet a disclosure requirement. In live mode the course's house rules apply the same way: every template section filled and AI use disclosed in Notes for Reviewers. Where a maintainer or owner asked something of this PR in the thread (a test, an approach, a question), the PR follows it or answers it. If the repo states no template, checklist or policy and no maintainer asked anything, this check passes. | required |
| Calibrated claims | The title and description's statements of certainty, coverage and impact, read against the test evidence and the diff (Standards and comms; Test evidence). | The title says what the change does. The description claims no testing, coverage, platform or impact the evidence does not show ("fully tested", "fixes all cases", "no regressions" without a run behind it), and any shortfall, failing check or deferred item is stated plainly rather than buried. | preferred |

## Verdict rule

Accept only if all five required checks (Plan fidelity, Decisive test evidence, Repo checks reported, Reviewable diff, Template and policy asks) pass. Any required check graded fail or unclear rejects the package. Grade unclear only when a source the check needs is missing from the package and the PR author could not have supplied it (for example, a bundle with no plan context); unclear is never a softer pass, and it counts as a fail. When the PR itself omits something a pass condition requires it to show or say, grade fail, not unclear. Calibrated claims is preferred: grade and report it, but it never changes the verdict. An honest shortfall is not a fail on its own: a PR that does less than the plan, skips a check or reports a failing one, and says so with the reason, can pass every required check.
